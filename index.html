Why this exists

Plain semantic search over Markdown notes misses the thing that makes Obsidian-style vaults useful: the [[wiki-links]] between notes. A pure vector search only finds notes that sound similar to your query — it can't follow a hop to a note that's related but phrased differently. Graph RAG fixes that by treating the link graph as a second retrieval signal.

Problem

Semantic search alone stops at the first hit. A note two links away that fully answers the question never surfaces because its wording doesn't match the query.

Idea

Use LangChain for the parts it's good at — loading, chunking, embedding, vector search — and LangGraph to explicitly orchestrate the extra "follow the links" step as graph state.

Payoff

The LLM gets both the notes that sound relevant and the notes that are structurally connected to them — a strictly richer context window.

How it's wired

LangChain owns document loading, chunking, embeddings, and the vector store. LangGraph owns the control flow: a small state machine with three nodes that runs the same way every time, so the steps are inspectable and easy to extend (e.g. add a re-ranker node without touching the rest).

Two retrieval signals feed the graph: the vector store (semantic similarity) and the link graph (structural relationships). graph_traverser is the node that makes this a graph RAG system instead of plain RAG.

Questions

Real questions asked while building this project, answered directly and shared here for the next person who wonders the same thing.

Q With 200k+ documents and a limited context window, does that mean we need LangChain/LangGraph more — and if we had enough context, would we not need them at all?

This conflates two different constraints. Context window size is a budget (how many tokens fit in one call). Corpus size — 200k documents — is a selection problem (which of those 200k things actually matter for this one query). A bigger budget doesn't make the selection problem go away.

200k markdown files is easily tens of millions of tokens — far beyond any practical context window, "unlimited" or not. And even where a huge context would technically fit everything, long-context research consistently shows models attend unevenly across very long inputs (the "lost in the middle" effect) — so dumping in everything degrades answer quality and blows up cost/latency for no benefit. You still want to hand the model the right handful of documents, not all of them.

Limited context (8k–32k)Very large / "unlimited" context
Still need retrieval to select relevant docs from 200k? Yes — no choice Yes — 200k files is still tens of millions of tokens
Still need graph_traverser-style link expansion? Yes, tightly bounded (small top_k) Yes, though you can afford a wider top_k
Still benefits from LangGraph's explicit multi-step control? Yes — essential to make every token count Yes — still the clearest way to avoid noisy context that "lost in the middle" punishes
What actually changes Chunk size / top_k must be small and precise Chunk size / top_k can be looser; less aggressive pruning needed
Bottom line: LangChain/LangGraph aren't a workaround for small context windows — they're for deciding what belongs in context at all, at any window size. That job gets more important, not less, as a corpus grows toward 200k+ files (see formula_qdrant_scale.md), regardless of how generous the context window is.

Q Why are related (linked) documents specifically important — why not just retrieve more documents?

Because "more documents" and "related documents" solve different problems. Retrieving more top-k results from a vector search still only surfaces notes that sound like the query — it just lowers the similarity bar, which mostly adds noise. It does nothing for the note that answers the question perfectly but uses different words, because a similarity score over word choice can't see a relationship that was never expressed in shared vocabulary.

A [[link]] is a different kind of signal entirely: it's the author explicitly saying "these two notes belong together," recorded at write time, independent of how either note happens to be phrased. That's what the comparison diagram above shows — pure semantic search misses [[Note B]] and [[Note C]] not because they're irrelevant, but because nothing in their wording matches the query; graph_traverser finds them anyway by walking 1–2 hops from whatever did match semantically.

Three concrete effects, mapped to the badges in that diagram:

  • Context breadth — reaches multi-hop context a single vector lookup structurally cannot, no matter how the similarity threshold is tuned.
  • Phrasing independence — a link survives vocabulary drift between notes written months apart on the same topic; embeddings alone are sensitive to exactly that drift.
  • Structural knowledge — every [[link]] a note-taker already wrote is free, hand-curated relevance signal; discarding it and relying on embeddings alone throws away work that's already been done.
Bottom line: retrieving more documents widens the net with the same mesh size; following related documents changes what the net can catch in the first place.

Q In the demo trace for "What powers Computer Vision applications?", why does the graph jump through Node 9 (Applications) to surface Node 5 (NLP) — and does that actually make the LLM's attention "better"?

Yes — Node 9 is the bridge. In the fixture graph, doc9_applications links to both doc4_cv and doc5_nlp, while doc4_cv only links back to doc9. So once semantic_retriever finds nodes 4 and 9 by wording alone, walking node 9's links is what reaches node 5 — a document that shares essentially no vocabulary with "Computer Vision applications" and would never have surfaced from embeddings alone.

Does this improve context sorting? Yes, and specifically how. Pure semantic search ranks purely by cosine similarity, which tends to return redundant near-duplicates of whatever hit first and has no way to reach a relevant-but-differently-worded neighbor. Layering graph_traverser on top adds a second, different ordering principle: after semantic search picks the entry points (4, 9), graph traversal appends structural neighbors (5) that share an explicit [[link]] — then generate_answer assembles the union into one context. The result is context organized by how the ideas actually relate in the vault, not only by how similar their wording is.

Does the attention mechanism itself get better? No — the transformer's self-attention math is unchanged. What changes is the material it has to work with. If Node 5 is never retrieved, no amount of attention can connect "Computer Vision" and "NLP" — the tokens simply aren't in the prompt. Once graph_traverser puts Node 5's text in the context window, self-attention can form cross-connections between the two topics that were structurally invisible to it a moment before. Retrieval isn't making attention smarter; it's removing a blind spot attention had no way to fix on its own.

Bottom line: a detective given five witness statements that all say "bank robbery" learns less than one given two statements plus the getaway driver's logbook a witness happened to reference. graph_traverser is what hands the LLM that logbook — the attention mechanism still has to read it, but it can't read what was never in the room.
